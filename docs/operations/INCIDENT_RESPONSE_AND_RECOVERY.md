# Incident Response and Recovery

## 1. Local incident categories

- Unexpected network connection
- Manuscript content in logs, previews, clipboard, or backup
- Cross-project data exposure
- Model package integrity failure
- Malicious file parser failure
- Malicious or ambiguous PDF extraction failure
- Project unlock or key failure
- Corrupted project or revision history
- Incorrect export or deletion
- Materially harmful translation/editing behavior

## 2. Immediate containment controls

The app must support local feature kill switches or configuration flags for:

- All AI processing
- Translation model
- Editing/review model
- Document import by format
- Decrypted export
- Archive restore

A privacy-integrity failure must lock affected projects and stop processing rather than continue with reduced protection.

## 3. Playbook: unexpected network activity

1. Stop manuscript processing.
2. Preserve metadata-only diagnostic evidence.
3. Identify binary/framework initiating connection.
4. Disable affected feature/build.
5. Verify whether any project was unlocked or processed.
6. Remove dependency or path.
7. Add regression test and rerun network capture.
8. Do not claim local-only privacy until verified.

## 4. Playbook: cross-project disclosure

1. Lock all projects and disable AI processing.
2. Preserve synthetic reproduction evidence without copying real manuscript text.
3. Identify cache/session/repository boundary failure.
4. Fix project-scoped state and clear caches.
5. Add direct and concurrent cross-project tests.
6. Review whether user notification is necessary.

## 5. Playbook: corrupted project

1. Stop further writes.
2. Verify immutable source snapshot and revision chain hashes.
3. Restore from last valid local checkpoint or encrypted archive.
4. Never overwrite the only known-good source.
5. Add failure-injection test for the exact operation.

## 6. Playbook: model integrity or harmful behavior

1. Disable the model role.
2. Verify package digest and provenance.
3. Roll back to prior approved model.
4. Re-run benchmark and affected adversarial tests.
5. Mark prior suggestions generated by affected version for review if necessary.

## 7. Recovery evidence

Every critical incident requires:

- Detection record
- Scope assessment
- Containment action
- Root cause
- Recovery validation
- Documentation update
- New regression test
- Updated release decision
